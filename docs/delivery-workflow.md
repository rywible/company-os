# Milestone delivery

Human approval fixes the outcome, boundaries, total agent-run allowance, review count and delivery policy. Agent roles determine capability and execution profiles. Foreman cannot approve its own milestones or change active boundaries. All retries, reviews, adjudication, acceptance and acceptance fixes charge the original milestone's allowance.

Implementation assignments receive server-generated `codex/milestone-<id>-work-<id>` branches from the current `codex/milestone-<id>` root after their dependencies have merged. Workers receive real Git clones with dependency installation, shell tools, tests/builds, root configuration, binary assets and deletions available within the approved assignment. They commit a clean working tree; the publication wrapper rechecks authority and pushes only the exact finished commit to the delegated branch. Source changes are published for repository CI to check. Creating the assignment PR emits the durable event that starts review. A PR completes implementation; only reviewed integration completes the assignment and releases descendants.

## Review limits

Two independent reviewers and two correction rounds are the defaults. Reviewers, adjudicators and code acceptance testers receive separate local checkouts pinned to the exact reviewed commit. They can inspect the whole project and run diagnostics, tests and supported game checks. Scratch files stay local; a reviewer cannot publish a code receipt. The application posts each review as an idempotent GitHub review comment attached to the reviewed SHA, including the observed check results. Reviewers return a structured ledger: stable ID, severity, defect category, concrete evidence, verification procedure, and open/resolved/dismissed status. Style and suggestions cannot block. Every later reviewer must explicitly account for prior blockers; the prompt restricts new blockers to material defects and regressions. Materiality remains model judgment, bounded by adjudication and hard attempt limits.

After the correction allowance, the Adjudicator role sees the requirements, exact diff, previous results, findings, and history. It may accept sufficient fixes, dismiss unsupported blockers, or prescribe one final correction. A separate verification by that role checks the final correction. Failure defers the assignment and its descendants; independent streams continue. No automatic replacement assignment resets a stopped review budget. Foreman discussions concern changed outcome, scope, or authority, not human PR review.

Publication is pinned to the reviewed commit. Replayed events cannot add another quorum, correction or PR. Saved pending outputs make publication retries reuse the original execution identity. GitHub comments carry idempotency markers. Polling detects missed head updates. Reviews are separate model runs using one GitHub identity, so they do not fulfill rules requiring approvals from distinct GitHub accounts.

## Integration and acceptance

Foreman writes acceptance criteria for every assignment and for the integrated milestone. Settings → Reviews has one optional “Requirements for every milestone” field. These company requirements are additive: the milestone shows them alongside Foreman's criteria, and approval snapshots them. Assignment criteria remain scoped to that assignment, so interfaces can unblock downstream work without needing the completed milestone. Acceptance and any acceptance correction must satisfy both the approved milestone criteria and the company requirements. Editing requirements affects future approvals, not active milestones. There is no project override.

Each repository managed by Company OS owns its automated checks in GitHub CI. Company OS consumes those results; it does not prescribe a language, test runner, check commands, or CI workflow. Changes to a managed repository's checks follow that repository's review process. This delivery feature does not install CI for the Company OS application itself. Managed repositories must run their checks on `codex/**` pushes, including integration branches, to produce results for the exact candidate commit. Use a connector token that can trigger workflows; GitHub's workflow `GITHUB_TOKEN` suppresses new push-triggered workflows. See [GitHub's trigger documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

The connector reads GitHub check runs, suites and commit statuses with pagination. Missing results, queued workflows and running checks defer the durable delivery without invoking another model or spending another acceptance attempt. Failed or cancelled results block integration; skipped/neutral results alone are insufficient. Repository checks are re-read immediately before merge. A CI failure enters the existing bounded correction process with the failure annotations and CI links supplied by that managed repository. Connector failures remain explicit workflow errors.

For games, Foreman must specify observable playtest criteria and supply actual evidence. Put automated playtest harnesses in repository CI and retain evidence in its logs/artifacts. A successful build does not establish that a playable milestone meets its criteria.

The adapter creates a merge candidate from the current target and reviewed head. It verifies that exact candidate, then updates the target to that commit with `force: false`. A concurrent divergent update rejects the fast-forward and requires a freshly tested candidate. Assignment integration has at most three candidate retries. The implementation uses GitHub's [branch merge API](https://docs.github.com/en/rest/branches/branches) and [non-force reference updates](https://docs.github.com/en/rest/git/refs); repository protection rules still apply. If direct updates are protected, the adapter opens an integration PR whose head is the tested candidate and merges through GitHub only when strict up-to-date checks also apply to administrators. Squash-only repositories receive an identical tested tree under a new commit SHA, with the original base verified; the superseded source PR is closed. Successful protected merges are recovered by their integration PR and tested tree if a response is lost. Insufficient permissions or outstanding required approvals surface as workflow failures or waiting deliveries rather than bypassing protections.

After all assignments merge, the system opens the milestone PR to main and waits for GitHub CI on its integration candidate. An Acceptance tester evaluates criteria, integrated source, and recorded results. A model approval cannot override failing checks. A failure creates one bounded corrective assignment by default, then repeats acceptance; the default is two acceptance attempts total. Exhaustion pauses the milestone. Main advances only to the accepted candidate. Deployment is not part of this policy.

Knowledge-only milestones use the independent acceptance role to evaluate their artifacts without creating empty code PRs. Old approved milestones retain their prior completion semantics; new approvals receive delivery-policy snapshots. Changing policy applies to subsequent approvals. Disabling engineering changes or automatic merging revokes those capabilities for active work too.

## Current execution boundary

Engineering supports complete replacement text files under `src`, `tests`, `e2e`, and `docs`, with TypeScript, CSS, Markdown, JSON, GLSL, GDScript and C# extensions. It does not grant dependency, root configuration, workflow, binary asset, deletion or deployment authority. Unsupported operations must be reported explicitly. Source snapshots are bounded by file/context limits and are not a new general-purpose coding harness. CI summaries and links are retained in milestone state; large playtest artifacts stay in repository CI. Legacy company acceptance text is migrated to additive milestone requirements; old app-managed command lists and project overrides are retired.

## Execution and allowance

A new plan must include one implementation run plus the configured independent review count per code assignment, two runs per analysis/inspection assignment, and one final milestone acceptance run. Approval revalidates against the current review setting and freezes it; corrections and failed-run retries need extra allowance. Historical approvals retain their existing limits.

The scheduler claims new deliveries whenever capacity is free; a slow invocation or PR poll does not hold idle worker slots. The worker pool still permits only one invocation on a Sprite at a time.
