# Operations and recovery

**Inbox** is the only triage queue. Its default **Open** view combines conversations, milestone approvals, blocked assignments, exhausted allowances, and grouped operational issues. Items remain visible after being read. The detail panel provides the next step, Archive for conversations, milestone decisions, and repair instructions or delivery retries. Linked milestone discussions are shown once; grouped system issues disappear when their checks recover. Read, Unread, and Archived filters remain available for conversations.

**Status** (`#Status`) is a quiet reference page for **In progress** and **System checks**. It has no separate review queue, attention count, or repair controls. A system issue can link directly to its Inbox entry. The authenticated `/api/operations` endpoint supplies the underlying summary. Alerts cover failed deliveries, jobs waiting longer than their threshold, stale worker authentication checks, and missing, failed or overdue restore checks. These are alerts inside Company OS, not external email or chat notifications. Job age is an indication to investigate, not proof that the process has stopped.

Storage migration 1 moves `context`, `contextHistory`, `result` and `pendingOutput` from the company-state JSON into `run_payloads`, preserving complete historical values. Domain reads load those values lazily. Metadata and changed payloads are saved in the same immediate SQLite transaction. Migration 2 adds saved operational checks and alert lifecycle records. `schema_migrations` records both versions; newer unknown versions refuse startup. Existing compatibility transformations still handle legacy domain records.

`GET /api/company` supplies up to 50 recent run summaries plus current active runs and runs belonging to the selected `thread` or `work`. It never includes saved run contexts, pending output, or replacement-file bodies. `GET /api/run/:id` retrieves a complete saved run. `/api/runs?before=<run-id>` pages backward in stable groups of 50. `/api/events?entity=<id>&before=<sequence>` filters before limiting to 100 events. Historical payloads remain retained for audit and recovery; no retention deletion is automatic.

One writer is required. Litestream copies SQLite asynchronously to the private Tigris bucket; it does not provide high availability or a zero-loss guarantee. A minute-by-minute replication marker lets restore verification detect a replica more than ten minutes behind. The monitor restores into a unique temporary directory each hour, checks SQLite integrity and the saved records, records the outcome, and removes only that temporary directory. It never replaces the live database. Failed checks retry after five minutes. `/healthz` is suitable for process liveness, while `/readyz` returns 503 when operational alerts exist; it should not be used to restart the writer for a downstream service problem.

Run a manual drill on the application Machine with `bun run verify:backup`. The result is saved in `operational_checks` and exposed in the operating summary. A pre-migration drill was completed on 2026-09-21 at 00:38:21 UTC: restored SQLite passed its integrity check, with 7 documents, 8 revisions and 13 saved runs. The latest company event was present. No live database was replaced.

For an actual recovery, stop the single writer and preserve its database, WAL and worker logs. Restore into a new volume or separate path, verify it, then start one writer with the matching application release. Do not downgrade the application across a storage migration: historical payloads moved out of the old JSON. Restore a pre-upgrade backup with its matching release if rollback is necessary.

After deployment, a second drill on 2026-09-21 at 00:58:40 UTC restored the migrated database, including all 13 separate run payloads. It again verified 7 documents and 8 revisions; the replica heartbeat was 52 seconds old. The production workspace response was 58,094 bytes and contained no saved historical contexts. An individual historical context remained accessible through its authenticated run endpoint. All three active workers and the wrela/wrela connector passed their access checks. The live implementation/reviewer checkout smoke test against wrela/wrela completed successfully, including native Git push and temporary credential cleanup.
